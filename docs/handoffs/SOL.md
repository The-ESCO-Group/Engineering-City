## Milestone 2 expanded 3D world

The main route is the city itself. The existing large procedural campus now has
an explicit semantic world index and materially functional map controls:

- all 18 core destinations and all 11 expansion zones are listed in the City
  Directory; semantic IDs are stable lowercase slugs and never renderer
  coordinates
- the 16 backend-enabled destinations are compile-time exhaustive against the
  generated `SemanticLocation` union; the remaining two core landmarks and all
  expansion zones stay explicitly visual-only
- each directory destination has a deterministic client-owned camera node and
  maps to one of the eight stable selectable world anchors, with direct and
  nearest-anchor relationships labelled separately
- expansion zones are marked “Mapped visual only” and do not pretend to expose
  unsupported backend workflows
- district/building selection runs a smooth, interruptible overview-camera
  flight; reduced motion jumps directly and reset restores the exact saved
  overview
- Infrastructure, Utilities, Environment, Security, and Mobility layers each
  change multiple real scene signals, including overlays and ambient channels;
  the current signals are explained by a compact live legend
- Auto, High, Balanced, and Performance quality modes control pixel ratio,
  shadows, frame budget, ambient-life density, label density, and tone-mapping
  policy; Auto resolves from local hardware hints
- High targets 60 FPS with a 30 FPS fallback, Balanced targets 45/30, and
  Performance targets 30/24. Browser automation retains a deliberately low
  headless frame budget for repeatable visual tests
- map orbit, pan, 360-degree inspection, zoom, reset, and optional bounded Walk
  mode remain available; Walk mouse-look has a keyboard-operable activation
  path, and City Directory provides a complete keyboard-accessible, non-3D way
  to inspect and focus destinations
- operating-system reduced-motion changes stop ambient travel and camera easing;
  modal/popover focus is moved, contained, and restored predictably

Ambient vehicles and pedestrians remain deterministic scene life rather than
engineering agents. They are filtered by quality and layer and never count as
workflow progress. Event-driven agent movement is Milestone 3.

## Milestone 3 event-driven workflow city

The city now renders a deterministic projection of the ordered project event
stream instead of the previous static agent fixture:

- a bounded pure reducer validates generated event envelopes, applies only
  contiguous sequences, buffers gaps, ignores exact duplicates, detects
  contradictory IDs/sequences, and produces a concise authoritative-resync
  request instead of guessing
- reducer state joins agents, tasks, locations, and the project work package by
  semantic IDs; `task.assigned` carries the client-owned travel destination and
  package state advances through intake, planning, review, validation, export,
  approval, and release events
- live and replay views share the same reducer; the timeline supports Go Live,
  play/pause, 0.5×/1×/2×, exact event scrubbing, sparse canonical sequence
  labels, and visible gap/stale/offline treatment
- the renderer resolves backend semantic locations to client-owned scene nodes,
  constructs stable orthogonal routes, offsets co-located agents, preserves
  deterministic replay, and jumps rather than travels when reduced motion or a
  paused scrub requires it
- engineering-agent movement is event-driven only. Ambient vehicles and
  pedestrians remain separate decorative city life and cannot increment task,
  agent, or package state
- active tasks appear as small carried work capsules and the project package
  moves independently between semantic districts with state-colored treatment
- every rendered agent is keyboard-selectable from a compact city dock; canvas
  selection is also supported. The inspector shows only reported assignment,
  location, status, blocker, public activity, and recent event facts, omits
  unavailable cost/model/confidence fields, and explicitly excludes private
  chain-of-thought
- the contract-shaped demo now contains 40 ordered workflow events covering
  assignments, travel, task state, a finding and approval gate, a change set,
  validation, export, an artifact, and a release candidate awaiting approval

## Milestone 4 traceable engineering workspace

The product shell now opens a single review workspace for project intake,
canonical engineering records, planning, changes, evidence, and human
decisions. The workspace consumes the existing engineering context through a
small adapter and keeps unsupported backend capabilities explicit:

- five-step guided intake persists a local draft, validates required fields,
  classifies uploads by role, records the selected project type, target,
  standards, restricted domains, and safety confirmation, and starts the live
  workflow only when the backend accepts every upload
- Files and Tasks views expose backend-shaped records, published task progress,
  blockers, assignment, and semantic city locations; a task can focus its
  district in the 3D city without coupling backend data to scene coordinates
- Requirements, Devices & I/O, Tags, and PLC views provide searchable,
  traceable Project Core records with exact source references, cross-links,
  coverage, confidence/provenance, and honest unavailable states
- Planning, Change Sets, and Revisions distinguish proposals from accepted
  revisions and show structured before/after impact across PLC, HMI, alarms,
  tests, and documentation without claiming that generated changes were applied
- Findings preserve fact, inference, discrepancy, parser warnings,
  limitations, confidence, linked records, and typed on-demand evidence; exact
  L5X locations and source metadata remain visible
- Approvals enforce the locally published decision/rationale policy, make live
  support for only Approve/Reject explicit, and keep broader demonstration
  decisions confined to the synthetic session
- every synthetic record is prominently labelled demo data and the workspace
  repeats the safety boundary: no direct PLC control, online editing,
  controller mode changes, forces, or live equipment actions

- 50 HTTP operations and one project WebSocket

### Districts implemented

The current world contains 26 procedural district specifications, eight
selectable workflow anchors, and 22 additional spatial labels. It provides a
dense central skyline, low-rise perimeter, roads, bridges, canals, utilities,
renewable energy, water treatment, testing, data-center, logistics, maintenance,
harbor, park, traffic, pedestrians, map orbit/zoom/reset, and bounded first-person

The directory now names every required destination. Requirements Hall, ESCO
Project Core, Template Library, Tag Foundry, Ladder Logic Lab, Alarm Center, and
Port Terminal have explicit projected labels plus deterministic focus mappings.

### Semantic location mapping

The stable selectable `BuildingId` anchor union remains intentionally small:

`intake`, `automation`, `hmi`, `electrical`, `qa`, `documentation`, `approval`,
and `release`.

The product-owned directory maps 29 lowercase semantic location IDs to exact
client-owned scene nodes and these stable selection anchors without storing
model- or backend-supplied coordinates. The generated backend contract enables
16 workflow locations. Agent occupancy, route animation, task capsules, and
project-package movement now come from the reducer projection of contract
events. Expansion destinations remain visual-only and cannot be produced by a
canonical backend assignment.

### Event types consumed

The frontend opens the project socket, resumes from a stored `seq`, invalidates
query groups for agent, finding, approval, report, and project/task events, and
persists up to 1,000 recent envelopes per project. It catches sequence gaps up
through REST, rejects duplicate sequence numbers, polls while connected, and
uses capped exponential reconnect backoff. A deterministic world reducer and
visible timeline controls are the next integration slice.

Missing reliability behavior:

- reconnect jitter
- persisted timeline playback controls
- typed ping/error frames
- acknowledgement/escalation treatment for approval, failure, and release events

The backend socket also has a replay-to-subscribe race that can delay one event
until the next reconnect.

### Performance baseline

- The world uses instanced/merged repeated geometry and quality-scaled ambient
  instance counts.
- Runtime quality selection controls pixel ratio, shadows, label density,
  ambient-life density, tone mapping, and the render-frame budget.
- Auto resolves to High on a typical capable workstation and targets 60 FPS;
  weaker hardware resolves to Balanced or Performance with a graceful 30 FPS
  class fallback.
- The city still constructs most static world geometry synchronously. Formal FPS
  sampling, progressive loading, and camera-distance LOD remain future
  optimization work.

### Accessibility baseline

a non-required Walk mode, a searchable/filterable non-3D City Directory with

Missing: keyboard-only approval coverage, motion-sickness presets beyond reduced
motion, and automated accessibility checks. Legacy shell areas outside the city
still contain small fixed typography, and the shell enforces an 1180-pixel

## Known limitations and product truth

- The city is driven by retained event history. A live project that has not yet
  emitted agent assignment/location/status events correctly shows no workflow
  agents rather than substituting decorative records.
- Ambient vehicles and pedestrians are deterministic decoration, not engineering
  agents. They must remain visually subordinate and must never imply workflow
  progress.
- Live browser integration is blocked by default backend CORS configuration for
  port 4173; the product can use a same-origin development proxy, but the
  documented backend origins must still be corrected for supported direct use.
- Generated contract types and a drift gate are present. The runtime adapter is
  intentionally product-owned; new endpoints must derive from generated schema
  types rather than adding parallel contract definitions.
- Do not label a generated report "verified" until a contracted validation level
  says so.
- The backend does not support direct PLC control, `.ACD` parsing, applying
  design changes, or raw model reasoning. The product will not add those
  capabilities.

## Requests for Claude

### CLAUDE-REQUEST-S001

Status: OPEN

Need: Allow the documented local frontend and every published HTTP method
through backend CORS.

Reason: The frontend runs at `http://127.0.0.1:4173`; backend defaults allow
5173 and 1420 only. Credentialed requests from the supported product origin fail
preflight. `PUT` is also absent although model configuration publishes a PUT
route.

Proposed schema/API: Add localhost and 127.0.0.1 port 4173 to configured origins
and add `PUT` to allowed methods. This is backend configuration, not a contract
shape change.

Acceptance criteria: Credentialed preflights for login, GET, multipart upload,
approval POST, and model-configuration PUT succeed from the documented product
origin.

### CLAUDE-REQUEST-S002

Status: OPEN

Need: Publish a lossless typed socket frame union and eliminate the
replay-to-subscribe race.

Reason: The client cannot safely discriminate ping/error frames, and an event
committed during socket handshake can be missed until reconnect.

Proposed schema/API: `WebSocketFrame = EventEnvelope | WebSocketHello |
WebSocketPing | WebSocketError`; subscribe before replay and discard queued
envelopes whose sequence is already sent.

Acceptance criteria: A concurrency test proves an event committed during
handshake is delivered exactly once, and generated TypeScript discriminates
every frame.

### CLAUDE-REQUEST-S003

Status: OPEN

Need: Stable semantic city locations and orchestration-driven movement events.

Reason: The frontend must never infer locations from model prose or coordinates.
The declared `agent.location_changed` event currently has no producer.

Proposed schema/API: Publish the supported semantic location IDs or expose a
location-capability endpoint; emit transitions at assignment, task start,
waiting/approval, completion, and release.

Acceptance criteria: The synthetic workflow produces deterministic, replayable
location events that map to known city nodes without coordinates.

### CLAUDE-REQUEST-S004

Status: OPEN

Need: Versioned intake and Project Core contracts.

Reason: Generic project attributes cannot safely represent the target profile,
standards, requirements, devices/I/O, tags, PLC, HMI, alarms, and tests required
by the product.

Proposed schema/API: Paginated revision-aware resources with source evidence,
cross-references, filters, stable deep-link identifiers, and explicit unsupported
states.

Acceptance criteria: The client can render and deep-link every canonical
engineering object without inventing a parallel schema.

### CLAUDE-REQUEST-S005

Status: OPEN

Need: Revisions, changesets, clarification resolution, and richer human decision
contracts.

Reason: The current approval request supports only a boolean and notes. It
cannot represent Request Changes, Accept Risk, or Defer, nor can it review a
structured before/after proposal.

Proposed schema/API: Changeset/revision resources, operations, evidence/risk,
dry-run conflicts and impact, clarification tasks, reviewer comments, and a
closed decision enum with required-rationale policy.

Acceptance criteria: Structured diffs and all required decisions are auditable,
permission-aware, and contract-generated.

### CLAUDE-REQUEST-S006

Status: OPEN

Need: Validation, release, artifact, and generation contracts.

Reason: Release readiness, real generation commands, import verification,
artifact trees, final approval, and a ZIP cannot be truthfully implemented from
the current report list.

Proposed schema/API: Revision-bound validation runs and gates; release
candidates; generation jobs; artifact metadata containing hash, generator,
target, validation level, diagnostics, and download; import-verification request;
final approval; release ZIP; corresponding events.

Acceptance criteria: Every Release Center control derives its availability and
disabled reason from backend data and every downloaded artifact is traceable.

### CLAUDE-REQUEST-S007

Status: OPEN

Need: Paginated audit reads and action capabilities.

Reason: The UI must not duplicate authorization policy or expose actions that
will inevitably fail.

Proposed schema/API: Project-filtered audit endpoint plus per-resource allowed
actions and exact disabled reasons.

Acceptance criteria: Audit Trail is readable and the UI can disable every
restricted action before submission with a backend-sourced explanation.

### CLAUDE-REQUEST-S008

Status: OPEN

Need: A stable delivery-plugin execution boundary owned by the backend.

Reason: Documentation describes a read-only plugin context, while the current
starter receives mutable `TaskContext`, directly accesses the database/storage,
and depends on edits in Claude-owned handler code.

Proposed schema/API: Claude-owned dispatcher and persistence adapter with an
immutable delivery context and typed result. Sol-owned plugins stay inside the
reserved delivery/reporting directories.

Acceptance criteria: Delivery runs after accepted human decisions without a
Sol commit modifying review handlers, orchestration, models, or storage core.

### CLAUDE-REQUEST-S009

Status: OPEN

Need: Reconcile contradictory historical sections in `docs/handoffs/CLAUDE.md`.

Reason: The document first states the completed backend and later says parsers,
workflow, agents, reports, and WebSockets do not exist. Endpoint counts and
plugin status are also stale in the historical section.

Proposed schema/API: Documentation-only correction with a single dated current
state and a separately marked historical roadmap.

Acceptance criteria: The handoff reports one unambiguous current backend state,
accurate endpoint/event counts, and current plugin limitations.
